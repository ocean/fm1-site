Can your firmware install V15 on a changed bootloader?

Felucca's update code only lets M-VAVE's update loader run when the package's boot area matches the FM-1's byte for byte. So an FM-1 whose bootloader has changed (m-bootloader, or M-VAVE's own Open V12 and V14 packages) can never get back to V15 over USB from your firmware. There's a fix, and for most projects it's a change to one file.

The check

In ota_stage() (firmware/src/ota.c in Felucca and its copies), a package that brings M-VAVE's loader, identified by its CRCs 0xEBAA and 0x5881 and its length 0x4DE1, has its first 0x4000 bytes compared with the FM-1's, 512 at a time. The first difference returns −5:

UPDATECHECK HEADFAILED

Some firmwares show nothing at all. Nothing has been written by then, so the FM-1 restarts into your firmware unharmed, but its owner's only way back to stock is the chip's USB download mode, from a computer. That's a dead end for anyone switching firmware from a phone.

To find it in your source, search for the comment the official loader writes the head: it must equal ours.

The fix

Charles Vestal's felucca-bsp afd83ede replaces the comparison with ota_boot_valid(). It accepts any well-formed FM-1 bootloader, every M-VAVE version and m-bootloader, and still rejects broken ones and other boards'. It only touches ota.c. What to do depends on how your firmware is built:

  • A Felucca fork, or your own copy of ota.c (most projects): port that commit into your ota.c. You don't need to rebase onto anything. Applied to Felucca 1.6.1's copy, 11 of its 12 hunks go in cleanly; the twelfth is two declaration lines.
  • On fm1-base: update it to 6c0b47e or later.
  • On felucca-bsp directly: update it to afd83ede or later.
  • A Felucca or X0X submodule: port the commit into the submodule's copy, or switch to a fixed base.

Felucca's main branch doesn't have the fix, so take it from felucca-bsp. felucca-bsp is MPL-2.0; using it doesn't relicense a GPL fork (see its LICENSING.md).

Tested on hardware

On an FM-1 with m-bootloader 1.2, DUB-1 1.3.0 (the old check) refused V15 after four reads: the package header, the loader header at 0xA5F00, then the boot area at 0x400. LOOM-8 0.8 (a fixed fm1-base) read the boot area's headers at 0x400, checked the bootloader from 0x4A0, and took V15 in 21 seconds.

Fix it with your coding agent

Paste this into Claude Code, Codex, Cursor or similar, from your firmware's repository. It ports the fix, keeps your own changes, and stops for your review before anything is committed.

This FM-1 firmware uses Felucca's USB update code. Please port one upstream fix into it.

The problem: in ota_stage() (usually firmware/src/ota.c; search the repo for the comment "the official loader writes the head: it must equal ours"), a package that brings M-VAVE's official update loader has its first 0x4000 bytes of flash.bin compared with the FM-1's own boot area, and any difference returns -5 ("CHECK HEAD / FAILED"). So an FM-1 whose bootloader has changed (m-bootloader, or M-VAVE's Open V12/V14 packages) can never install M-VAVE's V15 over USB from this firmware.

The fix: port commit afd83ede from https://github.com/hugelton/felucca-bsp (chip/ota.c, by Charles Vestal, tested on hardware). Fetch it with: git fetch https://github.com/hugelton/felucca-bsp main, then git show afd83ede -- chip/ota.c (or open https://github.com/hugelton/felucca-bsp/commit/afd83ede). It:
- adds ota_boot_valid(), which accepts any well-formed, bootable FM-1 boot area (every M-VAVE bootloader and m-bootloader) and rejects broken ones and other boards';
- replaces the byte-for-byte boot-area comparison with a call to it, for any package whose loader isn't Felucca's own;
- adds ota_jl_enc_k() and removes the now-unused OTA_LDR_* constants and the "official" variable.

How to do it:
1. Find this repo's copy of ota_stage(). If the update code comes from a git submodule (Felucca, X0X, fm1-base or felucca-bsp), tell me which and stop: the fix is to update or patch that submodule, and I'll decide how.
2. Apply the commit's changes to that file only. Expect it to apply almost cleanly to Felucca-derived copies; resolve any conflict by hand, keeping this repo's own changes and code style.
3. Keep any check this copy has that the commit doesn't touch, such as Felucca's "fl_len != OTA_FL_LEN" board-size check (-15). Tell me it's there: it also stops M-VAVE's Open V12/V14 packages and m-bootloader's installer, which upstream no longer refuses.
4. Don't change the path for Felucca's own loader (FELUCCA-LOADER-1): it never writes the boot area and needs no check.
5. Don't change licences or headers beyond crediting the fix: felucca-bsp is MPL-2.0, and this repo keeps its own licence. Add a short comment or commit message credit to felucca-bsp afd83ede.
6. Build the firmware with the repo's normal build and fix any warnings you introduced.
7. Show me the diff, and don't commit, push or release until I've reviewed it.

Then tell me how to test it on an FM-1: install the new build, then install M-VAVE's V15 over USB from it. It should be accepted ("UPDATE / CHECK HEAD / UPDATING / RESTART"). Testing on an FM-1 with m-bootloader proves the fix; on a stock bootloader it should still work as before. Don't claim it's tested until I've done that.

How this is made

The list began with a survey on 26 October 2026: GitHub code search for the update code's distinctive strings, the community firmware catalogues, and the fork lists of the most popular projects. Each project was classified by reading its source. Only DUB-1 and LOOM-8 were tested on hardware.

Since then, a scheduled job rechecks every project: its main branch's update code (following submodules and pinned bases), and its latest release's .fwsc package, which it unpacks and reads without running anything: Felucca's update code carries the string FELUCCA-LOADER-1, and the fixed code adds AC79BLID.

Fixed your firmware, or spotted a mistake? The next check picks up a fix on its own. To correct anything sooner, or for a project the job gets wrong, send a pull request to bootloader-check/overrides.json, with a reason. Corrections there are kept across every check.
