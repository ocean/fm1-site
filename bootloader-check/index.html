For FM-1 firmware developers

Does your firmware accidentally trap users whose bootloader has changed?

Installing firmwares built on Felucca's original update code can trap users whose FM-1 no longer has V15's bootloader: after M-VAVE's V16, now the official download, which brings its own; after m-bootloader; or after M-VAVE's Open V12 or V14. Their FM-1 will then refuse to install M-VAVE's stock firmware, V15 or V16, and usually every other firmware not built on Felucca, over USB (from the browser or an app). The same firmwares refuse V16 too, even on an FM-1 that still has V15's bootloader. The owner then has to either install a Felucca-based firmware that has the updated check, such as MIDIMON 0.4 or LOOM-8, which can then install V15 or V16, or use a computer to put the FM-1 into the chip's download mode and reflash it with a tool such as M-Flasher.

This matters more now that FM-1s are arriving with V16 already on them, and since autumn 2026 with the newer flash chip. Plenty of owners go straight from there to SLOOP, Skiff or JIANT and never go back to stock. They can keep switching between Felucca-based firmwares, which the original check lets through, so they may not notice anything until they try to go back to V16, or to a firmware not built on Felucca. On the newer chip, though, a firmware that only knows the older chip can lose their saves every time the FM-1 is switched off.

Nobody did anything wrong: V16 and m-bootloader work correctly, and the cause is a careful safety check in the original Felucca update code that assumes V15's bootloader is the only valid one.

Help keep switching easy

Good news: an updated check in hugelton/felucca-bsp keeps the protection and fixes this issue, Felucca itself has had it since 1.7.0, and usually you can port this fix to your Felucca-based firmware with a change to one file. Many firmwares also only know the older of the FM-1's two flash chips, which is a two-line fix.

The safety check

In ota_stage() (firmware/src/ota.c in Felucca and its copies), what happens to a package depends on the update loader (the writer) it brings:

Felucca's own loaderInstalls; the bootloader stays

FELUCCA-LOADER-1, used by the other Felucca-based firmwares. There's no boot-area check: it writes only the app area, so the bootloader stays as it is.

M-VAVE's update loaderRefused (−5) if the boot area has changed

Used by V15, and by M-VAVE's open firmware V12 and V14, and identified by its CRCs 0xEBAA and 0x5881 and its length 0x4DE1. The package's first 0x4000 bytes must be byte for byte the same as the FM-1's boot area, compared 512 at a time. That assumes M-VAVE's original bootloader is the only one.

Any other writerRefused (−3 or −7), with any bootloader

A package with no flash.bin, such as m-bootloader's own installer, gets −3: tested on hardware, it's refused after the package header, and the running firmware keeps running. One with a flash.bin and an unknown writer gets −7; that's from reading the code, since no such package has turned up.

Three ways the boot area changes

M-VAVE's V16V15 is refused, and so is V16 itself (tested on hardware)

V16, which M-VAVE's downloads page now serves instead of V15, brings its own bootloader: 12,655 of the boot area's 16,384 bytes differ from V15's. A Felucca-based firmware installed after V16 keeps V16's boot area, and the original check then refuses V15 (−5). Copies based on Felucca 1.6.1 also refuse V16 itself, whichever bootloader the FM-1 has (−15, the board-size check); older copies refuse it on V15's bootloader (−5), from reading the code. MIDIMON 0.4, with the updated check, took V15 over V16's boot area, and V16 over V15's. Tested on hardware with Felucca 1.6.1.

m-bootloaderOnly Felucca-based firmwares install (tested on hardware)

Its boot area never matches V15's or Open's, so every package with M-VAVE's loader is refused: the owner can't install V15 or Open, or any other firmware not built on Felucca. A Felucca-based firmware with the updated check installs, and can then install V15 (tested with ESTAMPIE 0.3.7 and LOOM-8).

M-VAVE's Open V12 or V14V15 is refused; a way out only before Felucca 1.6.1 (tested on hardware)

Open's package writes Open's own boot area, and a Felucca-based firmware installed after it keeps that boot area. The original check then refuses V15 (−5). Copies from before Felucca 1.6.1 can still install Open again over USB, since the boot areas match, and Open can then install V15, so there's a way out. Copies based on 1.6.1 also refuse Open (−15), so the only way out over USB is through a firmware with the updated check. Tested on hardware with Open V12; V14's boot area is byte for byte the same.

What the owner sees“CHECK HEAD / FAILED”, an error code, or nothing

UPDATECHECK HEADFAILED

Copies based on Felucca 1.6.1 show the code instead: “FAILED -5”, or “FAILED -15” for the board-size check, but nothing for −3. Some firmwares, such as ESTAMPIE, show nothing. Nothing has been written by then, and the running firmware keeps running. To switch away, its owner can install a Felucca-based firmware with the updated check, then V15; otherwise they have to use download mode, from a computer. With m-bootloader, hold REC while switching the FM-1 on. Otherwise, a flasher tool can ask the running firmware to restart into download mode (V15 and Felucca-based firmwares support this); the firmware's or the tool's instructions say how. Then a flasher such as M-Flasher can reflash V15 or Open.

The updated check

Charles Vestal's felucca-bsp afd83ede replaces the byte-for-byte comparison with ota_boot_valid(), which keeps the protection: it accepts any package whose bootloader is a valid FM-1 one (every M-VAVE version and m-bootloader) and any well-formed writer, and still rejects damaged bootloaders and other boards'. It only touches ota.c. What to do depends on how your firmware is built:

  • A Felucca fork, or your own copy of ota.c (most projects): port that commit into your ota.c. You don't need to rebase onto anything. Applied to Felucca 1.6.1's copy, 11 of its 12 hunks go in cleanly; the twelfth is two declaration lines. A 1.6.1-based copy also has a board-size check to look at (see the note under the table); the agent prompt below covers it.
  • On fm1-base: update it to 6c0b47e or later.
  • On felucca-bsp directly: update it to afd83ede or later.
  • A Felucca or X0X submodule: port the commit into the submodule's copy, or switch to an updated base.

Felucca itself has had this change since it moved onto felucca-bsp, from 1.7.0, so a Felucca fork can also take it by merging a newer Felucca. felucca-bsp is MPL-2.0; using it doesn't relicense a GPL fork (see its LICENSING.md).

Tested on hardware

On an FM-1 with m-bootloader 1.2, then with Open V12's boot area, then V16's: Felucca-based firmwares installed one another, M-VAVE's packages were refused, and the updated check took V15, V16, Open and m-bootloader's installer.
  • Felucca-based firmwares installed one another, and m-bootloader stayed: DUB-1 from V15, AMB-1 from DUB-1, and ESTAMPIE from AMB-1.
  • With the original check, M-VAVE's packages were refused: HYP-1 refused V15 (sent from FM-SWITCH on an iPhone); DUB-1 1.3.0 refused V15 after four reads (the package header, the loader header at 0xA5F00, then the boot area at 0x400); ESTAMPIE and Melodee refused V15; and AMB-1 refused Open V12.
  • After Open V12, whose package wrote Open's boot area over m-bootloader: DUB-1 (on Felucca 0.8-beta code) installed, refused V15 (CHECK HEAD / FAILED) and took Open V12 again, since the boot areas match. Felucca 1.6.1 installed, then refused Open V12 (FAILED -15, the board-size check) and V15 (FAILED -5). LOOM-8 0.8 installed from Felucca 1.6.1 and took Open V12, and later V15 over Open's boot area. V14 wasn't tested; its boot area is byte for byte V12's.
  • With V16's boot area (2 November): V16 took Felucca 1.6.1, which kept V16's boot area and then refused V15 (CHECK HEAD / FAILED). On V15's bootloader, Felucca 1.6.1 refused V16 at the header. MIDIMON 0.4, with the updated check, took V15 over V16's boot area, and V16 over V15's.
  • With the updated check, LOOM-8 0.8 (an updated fm1-base) read the boot area's headers at 0x400, checked the bootloader from 0x4A0, and took V15 in 21 seconds.
  • m-bootloader's installer (a package with no flash.bin) was refused by DUB-1 1.3.0 and Felucca 1.6.1 after the package header, with nothing on Felucca's screen, and both kept running. ESTAMPIE 0.3.7, with the updated check, took it (the installer showed ALREADY INSTALLED, since 1.2 was already there), then took V15 over m-bootloader.

The newer flash chip

FM-1s sold since autumn 2026 have a UC25HQ80 flash chip (JEDEC ID 0xB36014) instead of the first units' Puya P25Q80 (0x856014). Both hold 1 MB and take the same commands, but Felucca's code, and many firmwares built on it, check for the P25Q80 alone. On the newer chip, such a firmware usually keeps saves only until the FM-1 is switched off, and often can't install another firmware afterwards.

The fix is small: wherever your firmware checks the chip's ID, accept 0xB36014 as well, as Felucca's f4cbb6a2 does in persist_boot() (firmware/src/project.c). Felucca has it from 1.8.2, still a beta. The agent prompt below covers it too.

The Newer chip support? column in the list reads each latest release's code for the two IDs, as FM1Kit does: Both chips, Older chip for the first units' alone, or No check for a firmware that doesn't read the ID, so should save on either. It shows which chips the code checks for, not whether the firmware has been tried on a newer FM-1. To tell which FM-1 you have: on the newer ones, the M-VAVE logo is on the front, under the screen; on older ones, it's on the top, near the USB and MIDI sockets.

Fix it with your coding agent

Paste this into Claude Code, Codex, Cursor or similar, from your firmware's repository. It ports the updated check and the newer flash chip's ID, keeps your own changes, and stops for your review before anything is committed.

This FM-1 firmware uses Felucca's USB update code. Please port one upstream change into it, then check one small thing about the flash chip.

Background: in ota_stage() (usually firmware/src/ota.c; search the repo for the comment "the official loader writes the head: it must equal ours"), a package that brings M-VAVE's official update loader has its first 0x4000 bytes of flash.bin compared with the FM-1's own boot area, and any difference returns -5 ("CHECK HEAD / FAILED"); a package with any other loader that isn't Felucca's own is refused too: with -3 when it has no flash.bin (as m-bootloader's installer has none), or -7 when it has one. So on an FM-1 with a changed bootloader (the one M-VAVE's V16 brings, m-bootloader, or the boot area M-VAVE's Open V12/V14 writes), this firmware refuses V15 over USB. With m-bootloader it only installs other Felucca-based firmwares: V15, M-VAVE's open firmware and every non-Felucca firmware are refused, and the only ways to switch are a Felucca-based firmware with the updated check, or download mode. (On an FM-1 with V15's bootloader, it also refuses V16 and Open V12/V14, whose boot areas are different.) The check is a sensible safeguard; it just assumes M-VAVE's original bootloader is the only one, and m-bootloader itself works correctly.

The change: port commit afd83ede from https://github.com/hugelton/felucca-bsp (chip/ota.c, by Charles Vestal, tested on hardware). Fetch it with: git fetch https://github.com/hugelton/felucca-bsp main, then git show afd83ede -- chip/ota.c (or open https://github.com/hugelton/felucca-bsp/commit/afd83ede). It:
- adds ota_boot_valid(), which accepts any well-formed, bootable FM-1 boot area (every M-VAVE bootloader, V16's included, and m-bootloader) and any well-formed writer, and rejects damaged ones and other boards';
- replaces the byte-for-byte boot-area comparison with a call to it, for any package whose loader isn't Felucca's own;
- adds ota_jl_enc_k() and removes the now-unused OTA_LDR_* constants and the "official" variable.

How to do it:
1. Find this repo's copy of ota_stage(). If the update code comes from a git submodule (Felucca, X0X, fm1-base or felucca-bsp), tell me which and stop: the change belongs in that submodule, and I'll decide how.
2. Apply the commit's changes to that file only. Expect it to apply almost cleanly to Felucca-derived copies; resolve any conflict by hand, keeping this repo's own changes and code style.
3. Make sure the -3 line ends up as "if (!ota_off) return -3;", as in the commit: a package with no flash.bin, such as m-bootloader's installer, brings its own writer. If this copy is based on Felucca 1.6.1, that hunk may need applying by hand, because the "fl_len != OTA_FL_LEN" board-size check (-15) follows it. Make -15 apply only when the package has a flash.bin ("if (fl_off && fl_len != OTA_FL_LEN)"), but leave it in, and tell me it's there: it still refuses M-VAVE's V16 and Open V12/V14 packages (V16's flash.bin is 0xA9000 bytes, Open V12's 0x6F000 and V14's 0x73000, not 0x93000), which upstream accepts, and whether to relax it is my decision.
4. Don't change the path for Felucca's own loader (FELUCCA-LOADER-1): it never writes the boot area and needs no check.
5. Don't change licences or headers beyond crediting the change: felucca-bsp is MPL-2.0, and this repo keeps its own licence. Add a short comment or commit message credit to felucca-bsp afd83ede.
6. The flash chip: FM-1s sold since autumn 2026 have a UC25HQ80 flash chip (JEDEC ID 0xB36014) instead of the Puya P25Q80 (0x856014). Search the repo for 0x856014. Where the code accepts only that ID (Felucca's persist_boot() in firmware/src/project.c did), saves last only until the FM-1 is switched off on the newer chip, and installs can fail. Accept 0xB36014 as well, as Felucca commit f4cbb6a2 does (https://github.com/hugelton/Felucca/commit/f4cbb6a2), and list every place you changed. If there's no such check, tell me.
7. Build the firmware with the repo's normal build and fix any warnings you introduced.
8. Show me the diff, and don't commit, push or release until I've reviewed it.

Then tell me how to test it on an FM-1: install the new build, then install M-VAVE's V15 over USB from it. It should be accepted ("UPDATE / CHECK HEAD / UPDATING / RESTART"). Testing on an FM-1 with m-bootloader or V16's bootloader proves the change; on V15's bootloader it should still work as before. For the flash chip, on an FM-1 with the newer chip, save something, switch the FM-1 off and on, and check it's still there. Don't claim it's tested until I've done that.

How this is made

The list began with a survey on 26 October 2026: GitHub code search for the update code's distinctive strings, the community firmware catalogues, and the fork lists of the most popular projects. Each project was classified by reading its source. Several firmwares have since been tested on hardware: see Tested on hardware above.

Since then, a scheduled job rechecks every project: its main branch's update code (following submodules and pinned bases), and its latest release's .fwsc package, which it unpacks and reads without running anything: Felucca's update code carries the string FELUCCA-LOADER-1, and the updated check adds AC79BLID. It also looks in the firmware's code for the two flash chips' IDs, as 32-bit constants, the way FM1Kit does.

Updated your firmware, or spotted a mistake? The next check picks up the change on its own. To correct anything sooner, or for a project the job gets wrong, send a pull request to bootloader-check/overrides.json, with a reason. Corrections there are kept across every check.
