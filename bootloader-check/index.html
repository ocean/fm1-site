For FM-1 firmware developers

Does your firmware accidentally trap users who have changed their bootloader?

Installing firmwares built on Felucca's update code can trap users who have changed their FM-1's bootloader, usually to m-bootloader, or by installing M-VAVE's Open V12 or V14. Their FM-1 will then refuse to install stock V15, and usually every other firmware not built on Felucca, over USB (from the browser or an app). The owner then has to either install a Felucca-based firmware that has the updated check, which can then install V15, or use a computer to put the FM-1 into the chip's download mode and reflash it with a tool such as M-Flasher.

Nobody did anything wrong: m-bootloader works correctly, and the cause is a careful safety check in the original Felucca update code that assumes M-VAVE's original bootloader is the only valid one.

Help keep switching easy

Good news: an updated check in hugelton/felucca-bsp keeps the protection and fixes this issue, and usually you can port this fix to your Felucca-based firmware with a change to one file.

The safety check

In ota_stage() (firmware/src/ota.c in Felucca and its copies), what happens to a package depends on the update loader (the writer) it brings:

Felucca's own loaderInstalls; the bootloader stays

FELUCCA-LOADER-1, used by the other Felucca-based firmwares. There's no boot-area check: it writes only the app area, so the bootloader stays as it is.

M-VAVE's update loaderRefused (−5) if the boot area has changed

Used by V15, and by M-VAVE's open firmware V12 and V14, and identified by its CRCs 0xEBAA and 0x5881 and its length 0x4DE1. The package's first 0x4000 bytes must be byte for byte the same as the FM-1's boot area, compared 512 at a time. That assumes M-VAVE's original bootloader is the only one.

Any other writerRefused (−3 or −7), with any bootloader

A package with no flash.bin, such as m-bootloader's own installer, gets −3: tested on hardware, it's refused after the package header, and the running firmware keeps running. One with a flash.bin and an unknown writer gets −7; that's from reading the code, since no such package has turned up.

Two ways the boot area changes

m-bootloaderOnly Felucca-based firmwares install (tested on hardware)

Its boot area never matches V15's or Open's, so every package with M-VAVE's loader is refused: the owner can't install V15 or Open, or any other firmware not built on Felucca. A Felucca-based firmware with the updated check installs, and can then install V15 (tested with ESTAMPIE 0.3.7 and LOOM-8).

M-VAVE's Open V12 or V14V15 is refused; a way out only before Felucca 1.6.1 (tested on hardware)

Open's package writes Open's own boot area, and a Felucca-based firmware installed after it keeps that boot area. The original check then refuses V15 (−5). Copies from before Felucca 1.6.1 can still install Open again over USB, since the boot areas match, and Open can then install V15, so there's a way out. Copies based on 1.6.1 also refuse Open (−15), so the only way out over USB is through a firmware with the updated check. Tested on hardware with Open V12; V14's boot area is byte for byte the same.

What the owner sees“CHECK HEAD / FAILED”, an error code, or nothing

UPDATECHECK HEADFAILED

Copies based on Felucca 1.6.1 show the code instead: “FAILED -5”, or “FAILED -15” for the board-size check, but nothing for −3. Some firmwares, such as ESTAMPIE, show nothing. Nothing has been written by then, and the running firmware keeps running. To switch away, its owner can install a Felucca-based firmware with the updated check, then V15; otherwise they have to use download mode, from a computer. With m-bootloader, hold REC while switching the FM-1 on. Otherwise, a flasher tool can ask the running firmware to restart into download mode (V15 and Felucca-based firmwares support this); the firmware's or the tool's instructions say how. Then a flasher such as M-Flasher can reflash V15 or Open.

The updated check

Charles Vestal's felucca-bsp afd83ede replaces the byte-for-byte comparison with ota_boot_valid(), which keeps the protection: it accepts any package whose bootloader is a valid FM-1 one (every M-VAVE version and m-bootloader) and any well-formed writer, and still rejects damaged bootloaders and other boards'. It only touches ota.c. What to do depends on how your firmware is built:

  • A Felucca fork, or your own copy of ota.c (most projects): port that commit into your ota.c. You don't need to rebase onto anything. Applied to Felucca 1.6.1's copy, 11 of its 12 hunks go in cleanly; the twelfth is two declaration lines. A 1.6.1-based copy also has a board-size check to look at (see the note under the table); the agent prompt below covers it.
  • On fm1-base: update it to 6c0b47e or later.
  • On felucca-bsp directly: update it to afd83ede or later.
  • A Felucca or X0X submodule: port the commit into the submodule's copy, or switch to an updated base.

Felucca's main branch doesn't include this change yet, so take it from felucca-bsp. felucca-bsp is MPL-2.0; using it doesn't relicense a GPL fork (see its LICENSING.md).

Tested on hardware

On an FM-1 with m-bootloader 1.2, then with Open V12's boot area: Felucca-based firmwares installed one another, M-VAVE's packages were refused, and the updated check took V15, Open and m-bootloader's installer.
  • Felucca-based firmwares installed one another, and m-bootloader stayed: DUB-1 from V15, AMB-1 from DUB-1, and ESTAMPIE from AMB-1.
  • With the original check, M-VAVE's packages were refused: HYP-1 refused V15 (sent from FM-SWITCH on an iPhone); DUB-1 1.3.0 refused V15 after four reads (the package header, the loader header at 0xA5F00, then the boot area at 0x400); ESTAMPIE and Melodee refused V15; and AMB-1 refused Open V12.
  • After Open V12, whose package wrote Open's boot area over m-bootloader: DUB-1 (on Felucca 0.8-beta code) installed, refused V15 (CHECK HEAD / FAILED) and took Open V12 again, since the boot areas match. Felucca 1.6.1 installed, then refused Open V12 (FAILED -15, the board-size check) and V15 (FAILED -5). LOOM-8 0.8 installed from Felucca 1.6.1 and took Open V12, and later V15 over Open's boot area. V14 wasn't tested; its boot area is byte for byte V12's.
  • With the updated check, LOOM-8 0.8 (an updated fm1-base) read the boot area's headers at 0x400, checked the bootloader from 0x4A0, and took V15 in 21 seconds.
  • m-bootloader's installer (a package with no flash.bin) was refused by DUB-1 1.3.0 and Felucca 1.6.1 after the package header, with nothing on Felucca's screen, and both kept running. ESTAMPIE 0.3.7, with the updated check, took it (the installer showed ALREADY INSTALLED, since 1.2 was already there), then took V15 over m-bootloader.

Fix it with your coding agent

Paste this into Claude Code, Codex, Cursor or similar, from your firmware's repository. It ports the updated check, keeps your own changes, and stops for your review before anything is committed.

This FM-1 firmware uses Felucca's USB update code. Please port one upstream change into it.

Background: in ota_stage() (usually firmware/src/ota.c; search the repo for the comment "the official loader writes the head: it must equal ours"), a package that brings M-VAVE's official update loader has its first 0x4000 bytes of flash.bin compared with the FM-1's own boot area, and any difference returns -5 ("CHECK HEAD / FAILED"); a package with any other loader that isn't Felucca's own is refused too: with -3 when it has no flash.bin (as m-bootloader's installer has none), or -7 when it has one. So on an FM-1 with a changed bootloader (m-bootloader, or the boot area M-VAVE's Open V12/V14 writes), this firmware refuses V15 over USB. With m-bootloader it only installs other Felucca-based firmwares: V15, M-VAVE's open firmware and every non-Felucca firmware are refused, and the only ways to switch are a Felucca-based firmware with the updated check, or download mode. (On an unmodified FM-1, it also refuses Open V12/V14, whose boot area is different.) The check is a sensible safeguard; it just assumes M-VAVE's original bootloader is the only one, and m-bootloader itself works correctly.

The change: port commit afd83ede from https://github.com/hugelton/felucca-bsp (chip/ota.c, by Charles Vestal, tested on hardware). Fetch it with: git fetch https://github.com/hugelton/felucca-bsp main, then git show afd83ede -- chip/ota.c (or open https://github.com/hugelton/felucca-bsp/commit/afd83ede). It:
- adds ota_boot_valid(), which accepts any well-formed, bootable FM-1 boot area (every M-VAVE bootloader and m-bootloader) and any well-formed writer, and rejects damaged ones and other boards';
- replaces the byte-for-byte boot-area comparison with a call to it, for any package whose loader isn't Felucca's own;
- adds ota_jl_enc_k() and removes the now-unused OTA_LDR_* constants and the "official" variable.

How to do it:
1. Find this repo's copy of ota_stage(). If the update code comes from a git submodule (Felucca, X0X, fm1-base or felucca-bsp), tell me which and stop: the change belongs in that submodule, and I'll decide how.
2. Apply the commit's changes to that file only. Expect it to apply almost cleanly to Felucca-derived copies; resolve any conflict by hand, keeping this repo's own changes and code style.
3. Make sure the -3 line ends up as "if (!ota_off) return -3;", as in the commit: a package with no flash.bin, such as m-bootloader's installer, brings its own writer. If this copy is based on Felucca 1.6.1, that hunk may need applying by hand, because the "fl_len != OTA_FL_LEN" board-size check (-15) follows it. Make -15 apply only when the package has a flash.bin ("if (fl_off && fl_len != OTA_FL_LEN)"), but leave it in, and tell me it's there: it still refuses M-VAVE's Open V12/V14 packages (Open V12's flash.bin is 0x6F000 bytes and V14's 0x73000, not 0x93000), which upstream accepts, and whether to relax it is my decision.
4. Don't change the path for Felucca's own loader (FELUCCA-LOADER-1): it never writes the boot area and needs no check.
5. Don't change licences or headers beyond crediting the change: felucca-bsp is MPL-2.0, and this repo keeps its own licence. Add a short comment or commit message credit to felucca-bsp afd83ede.
6. Build the firmware with the repo's normal build and fix any warnings you introduced.
7. Show me the diff, and don't commit, push or release until I've reviewed it.

Then tell me how to test it on an FM-1: install the new build, then install M-VAVE's V15 over USB from it. It should be accepted ("UPDATE / CHECK HEAD / UPDATING / RESTART"). Testing on an FM-1 with m-bootloader proves the change; on a stock bootloader it should still work as before. Don't claim it's tested until I've done that.

How this is made

The list began with a survey on 26 October 2026: GitHub code search for the update code's distinctive strings, the community firmware catalogues, and the fork lists of the most popular projects. Each project was classified by reading its source. Several firmwares have since been tested on hardware: see Tested on hardware above.

Since then, a scheduled job rechecks every project: its main branch's update code (following submodules and pinned bases), and its latest release's .fwsc package, which it unpacks and reads without running anything: Felucca's update code carries the string FELUCCA-LOADER-1, and the updated check adds AC79BLID.

Updated your firmware, or spotted a mistake? The next check picks up the change on its own. To correct anything sooner, or for a project the job gets wrong, send a pull request to bootloader-check/overrides.json, with a reason. Corrections there are kept across every check.
